# S7, the reaper: status

The reaper (`middle_end/flambda2/reaper/`) is the whole-unit pass that
removes what is not used and unboxes what can be: a traversal builds a
flow graph of the unit (`traverse.ml`, `traverse_acc.ml`), Datalog rules
are solved over it (`points_to_analysis.ml`, `unboxing_analysis.ml`), and
the unit is rebuilt from the solution (`rebuild.ml`), with the types of
what the unit exports rewritten (`types_rewriter.ml`).

`PARALLEL-PLAN.md` kept S7 for later, with the idea of checking the
reaper's output with `validate_unit`, the analysis left unverified. This
stream does something else, on the human's request, in the way the
semantics treats Simplify: the parts of the reaper are transcribed in
Rocq, what they guarantee is stated in Spec files and proved, the
transcriptions are extracted, and a test tool runs them beside the
compiler's reaper on the same units and compares what the two compute.

- The traversal is a function from a unit to a finite graph
  (`FlambdaReaperTraversal.v`), a transcription of `traverse.ml`. The
  tool compares its graph with the one the compiler builds.
- The solution is an input, read off the compiler's Datalog database,
  as a decision of Simplify is read off the term after. Nothing is
  believed of it: an extracted check (`FlambdaReaperSolution.v`) tests
  that it is closed under the rules, and is proved to imply `closed`
  (`FlambdaReaperGraphSpec.v`). The least solution, which the engine
  computes, passes.
- The rebuild is a function of the unit and the solution
  (`FlambdaReaperRebuild.v`), a transcription of `rebuild.ml`. The tool
  compares its term with the one the compiler's reaper gives, up to
  bound names (`FlambdaCompareSpec.expr_eqb`), and runs both on the
  machine.
- The statement is that a unit rebuilt from a solution that passes the
  check refines the unit, run on its own (`program_refines`, or a
  relation of exits up to what can be observed, if the removal of
  unused value slots of escaping closures needs it).

A model of the same reaper on a language of its own was written before
this stream, outside this tree, with the proofs of the same statements
for that language and the counterexamples that it found. This stream
carries it over to the semantics of this tree, one part at a time.

## The plan

1. The flow graph and the rules (`FlambdaReaperGraphSpec.v`): the
   nodes, the fields, the relations of the graph, the tables of the
   solution, what it is for the tables to be closed under the rules of
   `points_to_analysis.ml`, and the finite forms of a graph and of a
   solution that the transcriptions and the tool exchange.
2. The traversal (`FlambdaReaperTraversal.v`), extracted.
3. The check of a solution (`FlambdaReaperSolution.v`, its Spec and its
   proofs), extracted.
4. The rebuild without changes of calling convention
   (`FlambdaReaperRebuild.v`): unused `Let`s removed, unused fields of
   blocks and unused boxed numbers made poison, unused value slots
   removed, unused parameters of continuations removed. Extracted.
5. The test tool and its examples: the tool runs Simplify and then the
   compiler's reaper on each example, converts the unit, the graph, the
   solution and the result to the model, runs the three transcriptions
   and compares.
6. The meaning of a solution (`FlambdaReaperFlowSpec.v` and its proofs):
   a relation between the values of the machine
   (`FlambdaSemanticsSpec.step`) and the nodes, kept by every step of a
   unit whose solution passes the check. The machine has no identity
   of allocations, so the relation says which allocation a value may
   come from rather than reading it off the value. Then the statement
   of the rebuild, and its proof.
7. Then, one at a time: changes of calling convention, unboxing of
   blocks and of closures, tupled code (`traverse_acc.ml`,
   `create_unknown_arity_tupled_call_witnesses`, with the edge that
   keeps a tuple alive, and an example that shows the edge is needed),
   exceptions, partial and over-applications, and the rewriting of the
   types.

## Done

- Step 1: `FlambdaReaperGraphSpec.v`.
- Step 2: `FlambdaReaperTraversal.v` (`traverse_unit`), with five
  examples; its header lists where it differs from `traverse.ml`.
- Step 3: `FlambdaReaperSolution.v` (`check_closed`,
  `check_field_used_exact`), its Spec and its proofs: what passes the
  check is closed, and meets `field_used_exact`; an example that is a
  least solution, and two that are not, show that neither statement
  holds for nothing.
- Step 4: `FlambdaReaperRebuild.v` (`rebuild_unit`,
  `rebuild_unit_from_tables`), the rebuild with the flag
  `-no-reaper-change-calling-conventions`, with three examples; its
  header lists where it differs from `rebuild.ml`. One difference is for
  the proof to settle: where the compiler drops the callee of a call
  that has no use (`rewrite_simple_opt`), the model, which has no call
  without a callee, keeps it, and its binding may have been removed.
  That happens only in code whose code id has no `any_usage`, which
  the proof is to show is never run. In the compiler the same case is
  what makes it stop with "Missing callee" on unused code (the model
  of the earlier work found the cause: every code is rebuilt, used or
  not).
- Step 6, first slice (`FlambdaReaperFlowSpec.v` and its proofs): the
  meaning of a solution, for units with no call, no closure and no
  code (`in_flow_fragment`). A value may be at a node ([flows]) if one
  of the allocations it may come from, existential since the machine
  has no identity of allocations, holds in each field what may be at
  the node of that field; every state that a unit reaches from empty
  environments, under a solution that passes `check_closed`, has each
  variable's value at the variable's node, and an exit's values at the
  nodes of the unit's continuations (`flow_sound`). What the rebuild
  will need follows: a bound variable has a source, and a read with a
  use makes the field read used in every allocation it may come from.
- Step 6, second slice: closures (`Closure_of_set`, the projections of
  value and function slots, static sets of closures) and direct calls,
  under the hypotheses that direct calls are full, of code that is not
  tupled, and with no extra argument for the exception continuation. A
  closure may be at a node through allocations of its set, one per
  function slot, each with its call witness; a call reads the witness
  through the closure, which makes the code it calls used, so the facts
  made conditional on that code hold. Local fields are covered only for
  units with no projection: with one, the statement is false, and
  `local_slot_counterexample` shows it on the machine. A closure stored
  in an immutable array and loaded back reaches its loaded variable by
  a use, not an alias (the default case of `traverse_prim`); a value
  slot then read from it through a local field gets no source, and the
  rebuild makes code that runs `Invalid`. The compiler does the same:
  the earlier model found it, and it was reproduced at `-O4` with a
  closure put in `[: clo :]` and read back with `Iarray.get`. Next
  slice: calls of unknown arity, partial and over-applications, and
  exceptions.
- Step 6, third slice: calls of unknown arity (`Indirect`), partial
  applications as values, over-applications, and exception
  continuations with extra arguments. A partial application may be at
  a node through a chain of unknown-arity witnesses, one per group of
  arguments given, matched group by group against the code's chain,
  each argument at the parameter at its place. The proof needs one
  fact of the machine that the graph cannot say: a partial application
  has fewer groups of arguments than its code has parameters (only
  `shape_of_code_call` makes one); without it a saturated partial
  application would route results and exceptions to the wrong call.
  Code with no parameter is out of the fragment: the traversal gives
  it one witness where the compiler stops with a fatal error, and the
  machine runs a call of it with arguments as an over-application,
  which the graph does not follow.
- Step 6, indirect calls of tupled code: the tuple that every call
  gives tupled code reaches the variable standing for it through the
  call's witness, and each field the code's parameter it is read into
  (`create_unknown_arity_tupled_call_witnesses`; the machine's
  `tuple_fields`). The two facts of the fix of #7072 only add uses, and
  the proof does not read them: `flow_sound_without_keep_alive` is the
  same statement for the graph without them, and
  `tupled_reverted_analysis_sound` says that, on the unit of
  `FlambdaReaperTupledSpec.v`, the solution whose rebuild goes wrong is
  a sound analysis. So what was unsound before the fix is the rebuild,
  which gives the code poison for a tuple whose fields it reads, not
  the analysis. Out of the fragment: direct calls of tupled code (no
  call kind of the model gives code the fields), and tupled code whose
  parameters are unboxed products.
- The statement of the rebuild, for the first fragment
  (`FlambdaReaperRebuildSpec.v` and its proofs): for a unit with no
  closure, no call and no code (`closure_free`), a solution that passes
  `check_closed` and `check_field_used_exact`, a unit whose names are in
  scope (`well_formed_unit`) and which gives its two continuations one
  value each (`exits_one_value`), the rebuilt unit refines the unit
  (`rebuild_refines`), exits compared exactly: a block that reaches an
  exit has all its fields used, and a symbol is compared as a symbol.
  Each of the two premises that are not about the solution's closure is
  shown needed: a unit that exits with two values has its second made
  poison (`exits_one_value_needed`), and a field said used though no
  rule gives it makes the rebuild box poison, which goes wrong
  (`field_used_exact_needed`). The first is for `C0-well-formed.md`:
  `well_formed_unit` does not count the values given to the unit's
  continuations, and where the compiler's traversal would stop
  (`List.iter2` in `apply_cont_deps`) the model's drops what is beyond.
- Why the statement of the rebuild does not yet go beyond the first
  fragment, with two counterexamples in `FlambdaReaperRebuildSpec.v`,
  each a unit that meets every premise of `rebuild_refines` but
  `closure_free`, whose rebuild does not refine it:
  - `closure_exit_counterexample`: a closure reaches an exit with a
    value slot that no projection names; the rebuild removes the slot,
    and the exit, which `refines` compares exactly, differs. What an
    exit is to be compared up to is a choice to make: the outside
    world cannot read a value slot (with local fields), so the
    statement for closures is to compare exits up to value slots, or
    to ask that no closure reach an exit, which a unit that raises a
    closure in an exception does not meet.
  - `wrapper_kinds_counterexample`: code whose body returns a value of
    another kind than its result arity says; the machine tests the
    arities of the call against those of the code, not the value
    returned, and the wrapper continuation of the rebuild tests the
    value against the call's return arity, so the rebuilt unit goes
    wrong. The premise needed, that what code returns has the kinds of
    its result arity, is one that `well_kinded_unit` gives and that no
    statement may take; a check of the term for it is for
    `C0-well-formed.md`.
- The statement for closures, chosen and stated
  (`FlambdaReaperRebuildSpec.v`): exits are compared up to what the
  outside world observes (`observed_equal`: closures without their
  value slots, through blocks, arrays, boxed numbers and partial
  applications; `program_refines_observably`), and a check of the term
  asks that what code returns have the kinds of its result arity, and
  the continuation a call returns to the kinds of the call's return
  arity (`results_kinded`). `rebuild_refines_observably` is proved for
  the first fragment, from `rebuild_refines`; the closure of
  `closure_exit_counterexample` refines up to observation, and the
  unit of `wrapper_kinds_counterexample` fails `results_kinded`. To
  prove it of closures, projections, static sets, code and direct
  calls is what is next; the Spec header lists what that needs.
  Comparing exits up to value slots is for review: it is the reaper's
  own reading of what a unit gives the outside world, and it is not
  `refines`.
- `rebuild_refines_observably` for units with closures
  (`no_code_no_slots`): sets of closures of several functions with no
  value slot, projections of function slots, static sets of closures,
  deleted code; with an example of each, rebuilt. A set whose closure
  has a source never becomes `Invalid` in a run, and a static set is
  kept whole where one of its symbols has a use.
- `rebuild_refines_observably` for units with value slots (`no_code`):
  sets of closures and static sets with value slots, and projections of
  value slots. The closures of the two runs are related as they are
  observed: the rebuilt closure has the slots the rebuild keeps, with
  related values; the example (`value_slots_example`) exits with a
  closure that has lost an unread slot, observed equal but not equal.
  A projection of a value slot into a variable of kind `Region` or
  `Rec_info` is left out: the rebuild keeps such a variable whether or
  not it is used, and not the slot it reads. The compiler makes no
  value slot of those kinds: closure conversion captures neither, and
  the backend stops on one (`to_cmm_set_of_closures.ml`).
- `rebuild_refines_observably` for units that bind code without calling
  it (`no_call`): the rebuild keeps the code of a code id with a use,
  rebuilt, and deletes the others (`code_example`).
- `exits_one_value` now checks calls too: a call to one of the unit's
  continuations returns one value, and passes no extra argument to its
  exception continuation. A call of code that returns two values to
  the unit's return continuation has its second result made poison
  (`call_exits_one_value_needed`). The compiler's units meet it, as a
  call returns what its continuation takes; a row for
  `C0-well-formed.md`, with the one for `Apply_cont`.
- `rebuild_refines_observably` for units with direct tail calls
  (`direct_tail_calls`): a direct call whose continuations lead out of
  the unit and which returns one value. The rebuild passes poison for
  a parameter with no use, and every argument it keeps has a use, so
  its variable is still bound: an escaping closure, which blocks the
  usage of the parameters through its witness, still has its arguments
  aliased to the parameters by a rule with no guard
  (`tail_call_example`).
- `rebuild_refines_observably` for units with direct calls that
  return to a handler of the unit (`direct_calls`), through the wrapper
  that the rebuild gives a call whose handler drops results
  (`wrapper_example`). Of `results_kinded` the proof uses only that the
  return arity of a call is that of its handler: the rebuild keeps the
  kinds of values, so the handler's own test of kinds gives the
  wrapper's.
- `rebuild_refines_observably` for units whose calls are all direct
  (`only_direct_calls`), whatever they return or raise to: a call may
  raise to a handler of the unit with extra arguments, of which the
  rebuild removes those the handler drops, from the call and from the
  handler, and keeps the exception (`raise_example`). An exception
  reaches its handler whole, and leaves the unit only through the
  unit's exception continuation, where it is compared as any exit. The
  machine raises only where the term does: an exception that a call
  raises on its own, such as `Sys.Break`, is not in the model, and the
  statement says nothing of it.
- `rebuild_refines_observably` for units whose indirect calls are full
  calls of code that is not tupled (`full_calls`): the rebuild passes
  poison for an argument whose parameter no code the callee may be
  uses, following the chains of call witnesses from what the callee
  may come from (`indirect_example`).
- `rebuild_refines_observably` for units with partial applications
  and over-applications of code that is not tupled (`generic_calls`):
  one proof for the shapes of a call of a closure, full, over and
  partial, with the arguments that a partial application holds
  (`partial_call_example`). `observed_equal` now compares the
  arguments of a partial application by kind only, as it compares
  closures without their value slots: a unit that exits with a partial
  application of code that does not use the argument it holds exits,
  rebuilt, with poison in its place, which only that code can read
  (`partial_exit_counterexample`; the former relation is
  `observed_equal_with_arguments`). A choice of what is observable, for
  the human to confirm.
- `rebuild_refines_observably` for units with indirect calls of tupled
  code, full or over-applied (`tupled_calls`, `tupled_call_example`):
  the two facts of #7072 give the tuple a use, so the rebuild keeps it,
  with poison in the fields that the code does not use; without them
  the rebuild of the example goes wrong. The machine reads every field
  of a tuple, used or not, so the relation of the two runs says that an
  unused field of a block is poison in the rebuilt run. That ends the
  calls. What the statement still asks that is not about the solution:
  `in_flow_fragment`, which leaves out the older forms of sets of
  closures and direct calls of tupled code (the compiler's, which give
  the fields, are not in the model); `tupled_calls`, which also leaves
  out static boxed numbers, strings and immutable arrays, which the
  compiler's units have, and arguments and projections of kind `Region`
  or `Rec_info`; and, met by the compiler's units, `well_formed_unit`,
  `exits_one_value` and `results_kinded`; and no projection where
  fields are local (`local_slot_counterexample`).
- Static boxed numbers, strings and immutable arrays of values
  (`static_constants`, `static_constants_example`), with the flow
  invariant widened to them. A static boxed number that holds a
  variable is left out, and must be: the traversal aliases its symbol
  to the constants and gives the variable no use, so the rebuild boxes
  zero in its place (`static_boxed_variable_needed`). The compiler does
  the same: in classic mode, closure conversion makes a static float
  block of a top-level record of floats with variables as its fields,
  and with `-Oclassic -flambda2-reaper -X reaper-oclassic=1` a program
  that prints `2.500000 1.000000` prints `0.000000 0.000000`
  (`traverse.ml` gives such fields no use; `rebuild.ml` writes zero).
- Toward the change of calling conventions: the simulation of the
  rebuild now runs on `rebuild_unit_cc`, under the hypothesis, for now,
  that no code changes, which the plain statements meet; three examples
  (`two_calls_example`, `poison_result_example`,
  `masked_return_example`) rebuild units where code loses parameters
  and results, called directly, through the wrapper, and in tail
  position, and their runs exit as the units do. Next: drop the
  hypothesis for code that makes no call in tail position, then for
  all code.
- Tupled code and the fix of #7072 (`FlambdaReaperTupledSpec.v`, its
  proofs, and the example `tests/semantics/reaper/
  tupled_unused_components.fl`): on a unit that gives tupled code a
  pair whose components it does not use, at unknown arity, the
  rebuild with the two facts that keep the tuple alive refines the
  unit (`program_refines`), and without them, the traversal as it was
  before the fix, the least solution passes the check and the rebuilt
  unit goes wrong, as the machine reads the fields of a tuple that has
  become poison: the model tells that reverting the fix is unsound.

- The change of calling conventions, with unboxing off
  (`FlambdaReaperCallingConventions.v`, its Spec and its proofs),
  extracted: the rules of `calling_convention_changes_rules` as a check
  (`check_cc_closed`, proved to give the closure of the rules) of the

- The unboxing of blocks and boxed numbers
  (`FlambdaReaperUnboxing.v`, its Spec and its proofs), extracted: the

## Choices to review

- The call kinds of the compiler `Indirect_known_arity` and
  `Indirect_unknown_arity` are one kind here, `Indirect`, which may make
  a partial application. The traversal reads an `Indirect` call as one
  of unknown arity, which is what the compiler builds for a call whose
  callee it does not know, and so, for a call of known arity, the graph
  of the model is not the compiler's; the tool reports such calls. A
  request to the core for the two kinds is the other way.
- A direct call is read as one of known arity. The statements are
  for units whose direct calls are full and call code that is not
  tupled (a check of the term), as the compiler makes them: the machine
  gives tupled code a tuple at every call, and the compiler's direct
  call of tupled code, which gives it the fields, is not in the model.

## Asked of other streams

Not yet written as requests; for the human to say whether they are.

- Of C0, a row of `well_formed_unit` (rule 5 of
  `requests/C0-well-formed.md`: a condition the compiler's units always
  meet is a row, not a premise). Each continuation of the unit is given
  one value: an `Apply_cont` to one gives one argument, a call that
  returns to one has a return arity of one value, and a call whose
  exception goes to one gives no extra argument. The compiler builds
  the unit's return continuation with one parameter, the module block,
  and checks nothing more. S7 keeps it as its own premise,
  `exits_one_value`, until the row exists; two counterexamples show it
  needed.
- Of C0, a decision for the human. `results_kinded` is a condition on
  kinds, which rule 5 says is never a premise; but without it the
  rebuild is not a refinement: the wrapper it gives a call tests the
  kinds of what the code returns, and the machine does not. The two
  ways: the machine makes a return of values of other kinds than the
  call's return arity undefined (a change to the core, after which
  `results_kinded` goes and `wrapper_kinds_counterexample` is a unit
  with no behaviour to refine), or S7 keeps the premise as an exception
  to the rule. The first is recommended: it is what the compiler
  does, which never tests the kinds of returned values. The proof for
  calls that return to a handler uses only the part of
  `results_kinded` that compares the return arity of a call with the
  parameters of its handler.
- Of the core, a call that may raise on its own, as the runtime makes
  one raise `Sys.Break` or `Out_of_memory`: an exception that the
  machine may give any call's exception continuation, which the
  statements of the rebuild would then cover; the traversal already
  gives the exception parameter of every handler a source.
- Of the core, the two call kinds `Indirect_known_arity` and
  `Indirect_unknown_arity` (see above), so that the graph of a call of
  known arity is the compiler's.
