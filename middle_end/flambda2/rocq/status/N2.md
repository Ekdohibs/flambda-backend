# N2: the freshness quantifier

What this file describes is merged, but for what it says is not in
this tree yet. It is in new files, and in a few files of other streams
that their owners gave leave for, named where they are. A second piece
of work, not about names: rewriting in a handler or in the body of
code from the states that have a predicate (the last entry under
"Done"). A third: the rewrites of the validation keep scope (its own
section below). A fourth: a normalisation written for the validation,
which does not apply it yet (the last section).
The human's question: can the quantifier of the papers on nominal
sets, the reversed N that reads "for all but finitely many names", be
used here, and does it make statements easier? The answer, the survey
and the recommendation are in `requests/N2-fresh-quantifier.md`.

## Decided overnight

- The names: `for_fresh` for the definition, `И` for the notation,
  `supports` for "a finite set of names supports a predicate",
  `propositions` for `Prop` as a type that contains no names,
  `concretion` for the scope of an abstraction opened at a name. To
  change one is a renaming in files that nothing else imports.
- The explicit forms stay primary and the quantifier is a derived
  layer (the recommendation; N1 agrees for its interface; D39).
- Lists of bound names are treated when they repeat no name, which is
  row 5 of well-formedness (`FlambdaBindersSpec.binders_distinct`).
- The new statements about free names use the lists of
  `FlambdaBindersSpec.v` (`among z (free_variables_of_expr body) =
  false`), not the older relations, since fresh names are made from
  lists.
- The converse is stated with the two conditions of well-formedness as
  premises on both terms, as N1 gave it: it is for the terms that
  well-formedness admits. That neither can be left out is N1's two
  statements in `FlambdaCompareAlphaSpec.v`, which the header cites.
- `fresh_names` and `fresh_names_fresh_statement` are in
  `FlambdaFreshQuantifierSpec.v`, moved from its Proofs file: a
  function that makes names is in a statement of
  `FlambdaInlineFreshSpec.v`, and a Spec file may not import a Proofs
  file. It changes a Spec file that is merged and signed, by one
  definition and one statement; R1 is asked to confirm them. N1
  agreed, and does not want it in its own Spec.
- Two choices of fresh variables in inlining are related by
  alpha-equivalence, not by "the second is the first renamed": the
  variables made are bound in the result, and a fresh variable may
  occur bound in the body of the code. N1 agreed that this is the
  right reading of its fourth form.
- The names `FlambdaAlphaFresh*` and `FlambdaAlphaGroup*` match the
  pattern `FlambdaAlpha*` of N1's section of `OWNERS.md`, and
  `FlambdaCompareConverse*` the pattern `FlambdaCompare*` of V1's. They
  are N2's files, N1 agreeing; they are listed by name in N2's
  section, as `FlambdaCompareAlpha*` is in N1's. To rename them
  instead costs a renaming of files that nothing else imports.
- The equivalences at the binders (`FlambdaAlphaFreshSpec.v`) take the
  same two conditions, on the two terms compared, though the direction
  from right to left uses less (the entry under "Done" says what). One
  form of premise for every statement is easier to use on well-formed
  terms; to split each into its two directions with the least premises
  would add five statements and change none.

- For `FlambdaContextWhere*`, with C0 and T2 agreeing:
  - The hole is asked two things in every state in which it can come
    to run: that it refines from the states that have the predicate,
    and that the two expressions have the predicate together there.
    The second is what the proof needs: it goes through a state with

    parameters, since the machine does not test them, and the

    kinds there.
  - The names on the code side that `FlambdaNormaliseProofs.v` uses
    (`binding_related`, `Codes_related`, `statics_related` and the
    like) stay, as the instance at a relation that ignores what the
    code binds; the general inductives are `codes_related_where`,
    `binding_related_where` and `statics_related_where`.
  - `FlambdaContextProofs.v` does not import the new Spec: its

    `FlambdaContextWhereProofs.v` takes them at the definitions of

## The continuations of a handler, bound outside it

`FlambdaLiftContsSpec.v` with `FlambdaLiftContsProofs.v` and
`FlambdaLiftContsNamesProofs.v`, and `FlambdaLiftContsScopeSpec.v` with
`FlambdaLiftContsScopeProofs.v`: three statements, proved with no
axiom and no `Admitted`. A normalisation written for the validation.
Nothing applies it and it is extracted nowhere.

- The shape. Each application of a continuation `k` gives one of its
  parameters a constant, and the handler of `k` tests that parameter by
  a `Switch`, having first bound continuations of its own that the arms
  apply. The front end leaves this where a variant is matched after the
  branches that build it have met. An application of `k` cannot go
  where the arm of its constant goes while that arm applies a
  continuation that is in scope in the handler only.
- `lift_handler_conts` binds those continuations outside the `Let_cont`
  of `k`, the first bound first. Each takes, in front of its own
  parameters, the parameters of `k` that its handler may read, under
  their own names and with their kinds, and each of its applications
  gives it those. The handler of `k` is then the `Switch` itself. No
  name is made and nothing is copied.
- `lift_handler_conts_equivalent_statement`: the result is equivalent
  to the term under all environments, with no premise.
  `lift_handler_conts_equivariant_statement`: the pass commutes with
  every renaming, exactly. `lift_handler_conts_keeps_scope_statement`:
  it keeps scope.
- The proof of the equivalence takes one continuation at a time, in
  two steps. The continuation first takes the parameters where it is,
  one at a time. Each is N3's equivalence of
  `FlambdaUnaliasParamsProofs.v` read from right to left: a
  continuation with one parameter more, which every application gives
  one variable, is the continuation whose handler begins with a `Let`
  of the parameter to that variable. It holds in the states where the
  variable has a value of the kind, and the handler of `k` is entered
  in such a state. N3's equivalence is of a parameter whose name is
  not the variable given, so the proof goes by a parameter with
  another name (`FlambdaNameAbstractionSpec.fresh_name`); that name is
  in no term that the pass returns. The continuation then reads no
  parameter of `k` that it does not bind itself, and goes out of the
  handler: `FlambdaSinkContsProofs.let_cont_into_handler`, the other
  way.
- What the pass tests is listed in the header of the Spec. Four of the
  tests are there for use, and the proofs do not need them: that `k`
  is not an exception handler; that every application of `k` gives
  the tested parameter a naked immediate; and the two tests of the
  section below.

Not done: the validation does not apply the pass. Alone it changes
what a term looks like and no more. It is of use in front of a
forwarding that takes an application of `k` to the arm of its constant
where the handler of `k` is the `Switch` itself, and, in the term
after, with the binding of a parameter that every application gives
the same constant; neither is in this tree. Putting the pass in a
round changes definitions that landed statements reach, and is a
second series.

## The body of code, from the states in which the callee has its code (2026-11-13)

Asked by C3 for the second stage of its copy of code, and ruled by the
orchestrator. C3 rewrites the body of code by what is known of
`my_closure` from the code itself: that it is a closure of that code.
`let_static_code_refines_from_statement` could not be used for it: its
premise (`code_refines_from`) asks the two bodies to refine, and to
have the predicate together, in every state in which the parameters
are bound to values of the right kinds and `my_closure` to any value
of kind `Value`.

- `code_refines_from_called inv id params my_closure ret exn metadata
  source target` (`FlambdaContextWhereSpec.v`) is that premise asked
  of fewer states: those in which, besides,
  `closure_of statics callee = Some (id, value_slots)` for some value
  slots, `statics` being the static environment of the state in which
  the body runs.
- `let_static_code_refines_from_called_statement` is
  `let_static_code_refines_from_statement` with that premise, `id`
  being the code id that the `Let_static` binds the body to. Proved
  (`FlambdaContextWhereProofs.let_static_code_refines_from_called`).
- It gives the statement that was there: two bodies that have the
  old premise have the new one for every code id
  (`code_refines_from_called_of_from`,
  `let_static_code_refines_from_of_called`).

Why it holds: a call finds the body that it runs by the code id of
its callee (`FlambdaSemanticsSpec.shape_of_closure_call`), so the body
bound to a code id runs in no other state. For the proof the relation
between the bodies of code in C0's `FlambdaContextProofs.v` takes the
code id that the code is bound to, and the hypotheses about it are
handed `closure_of statics callee = Some (id, slots)`, which the
induction (`transfer`) has where it uses them. Changed by C0's leave,
as a commit of its own, with C0's word on the hunk of its file. No
statement of a Spec changed; every lemma of that file that another
file uses kept the text of its statement, and no other file changed.

What the premise does not give, from R3's reading of the statement
(passed to C3):

- `bind_params params vs [(my_closure, callee)]` binds the parameters
  over `my_closure`: where a parameter has the name of `my_closure`,
  that variable holds the parameter's value in the body and not the
  callee. A rewrite that reads `my_closure` needs it not to be among
  the parameters.
- Nothing about the value slots: not which there are, and not that
  two closures of one code id have the same.

### Decided (2026-11-13)
